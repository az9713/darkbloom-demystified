Darkbloom in Plain English

This page tells the whole Darkbloom story in prose, with no tables and no jargon left unexplained. Every number here is real and comes from the paper or the code. The detailed pages under concepts/ back each claim with file and line references.

The idea

There are more than 100 million Apple Silicon Macs in the world, and most of them sit idle most of the day. Each one carries a surprisingly powerful chip with up to hundreds of gigabytes of fast shared memory — enough to run large AI models at conversational speed. Darkbloom connects that sleeping capacity to people who need AI answers, and pays the Mac owners for the work.

The obvious objection arrives immediately. If my prompt runs on a stranger's Mac in a stranger's home, the stranger can read it. They own the machine. They have the administrator password. They can plug things into it. Darkbloom's entire reason to exist is making that objection false.

The trick: remove the doors instead of hiding the room

Expensive data-center chips solve this problem with special hardware that encrypts memory while programs run. Apple's chips cannot do that for outside software. So Darkbloom does something different, borrowed from Apple's own Private Cloud Compute: instead of encrypting the room, it removes every door.

Think of the Mac owner as a landlord with keys to every room in the building. Darkbloom builds a room with no doors at all. The work happens inside one single program — the AI model, the network connection, and the decryption key all live inside the same process, in the same protected memory. There is no second program to spy on, no local network traffic to record, no pipe between processes to tap. On the private path, the only helper programs it ever launches are security checks that never touch your data.

Then three locks from Apple's operating system seal that process. First, the program tells the operating system's core — the kernel — to permanently refuse all debugger connections, even from the administrator. Second, the program is signed in a way that makes the kernel reject any attempt by another program to read its memory. Third, a macOS feature called System Integrity Protection, SIP, stops even the administrator from switching those first two locks off.

Here is the elegant part, and it is a genuine proof, not a slogan. The only way to turn SIP off is to restart the Mac into a special recovery mode. But restarting kills every running program — including the Darkbloom process, whose secrets exist only in memory and die with it. So if the protections were on when the process started, they stay on for as long as the process lives. Checking once at startup is mathematically enough; the software still re-checks on every request anyway, which costs all of 12 milliseconds.

What remains for a truly determined attacker? Physically unsoldering the memory chips to probe them — which destroys them, because Apple solders memory directly into the processor package. Apple accepts exactly the same residual risk for its own private AI cloud. Everything short of a soldering iron is engineered out.

The journey of one prompt

You send a question using any standard AI app or library — Darkbloom speaks the same dialect as OpenAI's API, so most software works after changing one web address. Your question travels over an encrypted connection to the coordinator, Darkbloom's traffic-control service in the cloud.

The coordinator must briefly see your question in plain form. It has honest reasons: it counts the words to bill you, checks your balance, and picks the best Mac for the job. It never writes your question to any log or database, and it forgets the request's keys the moment the answer finishes. Then it wraps your question in a fresh, single-use envelope of encryption — a new random key for every single request — addressed so that only one specific program on one specific Mac can open it. Even the Mac's owner, watching their own network cable, sees only scrambled bytes.

The doorless room on that Mac opens the envelope, runs the model on the Apple graphics chip, and streams the answer back, each piece encrypted again for the return trip. When the request ends, the program deliberately overwrites the memory that held your words, using a function the compiler is forbidden to optimize away.

One honesty note the project itself insists on: this is relay encryption, hop by hop, not sealed end-to-end. And the docs must be more honest still. The design calls for the coordinator to run inside a special cloud machine whose memory even its operator cannot read. The deployment documents in the repository admit production is not there yet — today's cloud machine has a weaker protection level, and an operator with maintenance access could technically reach that brief plaintext moment. Nothing is stored, and policy forbids looking, but today that promise rests on policy, not physics. The stronger hardware is the stated plan.

Trust, or how to believe a stranger's computer

Encrypting to a Mac only helps if that Mac is genuinely secure and running genuine software. But the person reporting all this is the very person you distrust. Darkbloom's answer is five independent witnesses.

The first witness is a special security chip inside every Apple Silicon Mac, the Secure Enclave, which signs statements with a key that physically cannot leave the chip. That proves which machine is talking. The second witness is macOS itself: through Apple's device-management system, the operating system — not the owner's software — reports whether the security locks are on. The third witness is Apple the company: its servers issue a signed certificate vouching that this is real Apple hardware with real security settings, and forging that would mean breaking Apple's own certificate authority. The fourth witness is time: every five minutes the coordinator issues a fresh challenge, and a Mac that rebooted to weaken itself gets caught and expelled immediately, with no grace period.

The fifth witness is the cleverest, because it solves a problem Apple never gave Mac developers a tool for: proving which program is running. Darkbloom repurposes Apple's push-notification service. Apple's own kernel gatekeeper only delivers a push notification to a program whose signature, identity, and entitlements all check out — a tampered or imitation program simply never receives it. So the coordinator encrypts a random number, sends it as a push notification, and waits. Only the genuine Darkbloom program can receive the push, decrypt the number, and sign it back with the security chip. A lying fork of the software fails this test not because it is caught lying, but because the test never reaches it.

Only a Mac that satisfies all five witnesses ever receives private traffic. In the code this is one single gate function every request must pass; there are no exceptions, not even for your own machine.

How a Mac joins — nobody "discovers" it

A natural question: how does the network find all these Macs in people's homes? The answer is that it never does. There is no scanning, no probing, no directory of machines waiting to be found. Every Mac in the fleet is there because its owner typed one command, and the machine then introduced itself — always dialing outward, never answering a knock.

The joining ritual goes like this. The owner runs a single install command in the terminal. The script downloads the Darkbloom software and refuses to run it until two checks pass: the download's fingerprint — a SHA-256 hash — matches the published one, and Apple's own code-signature verification confirms the program is the genuine, notarized build. The script then reads the Mac's serial number from the system and asks the coordinator for a personalized enrollment profile made for exactly that machine.

Installing that profile is the moment of consent, and macOS makes it explicit: the system shows the owner precisely what the profile grants before anything is installed. What it grants is deliberately tiny — of the thirteen powers Apple's device-management system can hand out, Darkbloom requests only the three that ask questions: inspect the device, read its basic information, and read its security settings. The powers that act — erase the device, lock it, install software, change settings — are all explicitly withheld. The management server can interrogate the Mac; it can never touch it.

Next, the owner runs a login command. The Mac displays a short code; the owner types that code into the Darkbloom website while signed in to their account. That is the whole linking ceremony — an internet standard called the device-code flow, the same pattern a TV app uses — and it ties this machine to this owner for earnings and for the free use of one's own hardware.

From then on, the Mac does all the talking. It opens one outgoing connection to the coordinator — outgoing is the key word, because a home router happily allows calls out while blocking calls in, so no port forwarding and no firewall changes are ever needed. Over that connection the machine presents its credentials: the signed statement from its security chip, its encryption key, its push-notification address, and honest facts about its hardware — which chip, how much memory. The five witnesses from the previous section then interrogate everything it claimed. After that, a steady heartbeat tells the coordinator what models the machine holds in memory and how much real capacity its engine can take, and only then does paying work start to flow.

Leaving is as undramatic as joining. The owner can stop the program at any moment, mark the machine as private so it serves only its own owner, or remove the enrollment profile in System Settings — which deletes the management link and its certificates immediately and completely. A vanished Mac simply stops heartbeating; the coordinator routes around it within seconds, and any request it was holding quietly restarts elsewhere.

The fleet and the money

The network itself is a swarm of home computers behind home routers, and the engineering embraces that. Every Mac dials out to the coordinator — no port forwarding, no firewall changes — and reports a heartbeat with its true, engine-measured capacity. The coordinator estimates, in milliseconds, how long each eligible Mac would take to finish your request, and picks the cheapest. If the chosen Mac dies before producing a word, your request silently retries elsewhere; if it is slow to start, a backup Mac races it. A quiet controller watches demand and tells Macs to pre-load models before the next wave arrives. Measured on real hardware: 92 tokens per second on an M4 Max, first word in about a second and a half.

The money is deliberately boring, which is what you want from money. Everything is counted in millionths of a dollar, in whole numbers, so nothing rounds away. Before a request runs, its estimated cost is set aside from your balance; afterwards the exact cost is settled and the difference refunded. A dishonest provider inflating its numbers hits a hard ceiling — the bill can never exceed twice the estimate — and completed work that reports zero tokens bills you nothing and raises an alarm. During the alpha, providers keep one hundred percent of what their Macs earn, and a Mac owner using their own machine pays nothing at all. There is even a pool-funded base income for reliable machines, tiered by verified memory — about the price of a Netflix subscription per month for a 64-gigabyte Mac — capped so nobody can farm it with fake hardware, because the memory claim is checked against Apple's own records for that serial number.

Why do the economics work at all? Because modern "mixture-of-experts" models only wake a small fraction of themselves for each word, and consumer chips with big shared memory are perfect for that shape. For those models, electricity on a Mac costs six to thirty-two times less per word than renting the equivalent from a cloud API.

What it does not do

Darkbloom's docs are at their best when they say this plainly, so this page ends the same way. The owner cannot read your words, but can see their timing, which leaks roughly how long your question and answer were. The whole edifice assumes Apple's kernel has no unpatched hole. Apple itself is a single point of trust five times over. Nobody can yet cryptographically prove the model computed your answer correctly — billing and correctness both rest on detection and clamps, not proofs. And the coordinator's hardware privacy shield, as noted above, is still the design rather than the deployment.

That is the technology: a room with no doors, on a stranger's computer, vouched for by five witnesses, paid in millionths of a dollar. The rest of this site walks the same ground with file names and line numbers — start with the overview, or go straight to the questions you did not know to ask.
